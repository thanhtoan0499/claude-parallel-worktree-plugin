# What still keeps port 4400 alive

`bin/dashboard.py` (920 lines) + `bin/dashboard.html` (1343 lines) serve a localhost-only
dashboard on `http://127.0.0.1:4400`. The design direction on record is to retire it: it needs a
process kept alive, it is reachable from exactly one machine, and three separate bugs on
2026-09-07 (a shared cache lock that froze every endpoint behind one slow subprocess, a duplicate
top-level `const` that rendered the page blank, a background process silently reaped) came from
it existing at all.

Answering an escalation was the last thing the CTO *had* to go there for. As of this change the
published board can do it: the page writes the chosen option to the artifact db's
`escalation_answers` collection and `bin/systemd/board_mirror_answers.py` brings it down into
`~/.claude/hermes/escalations.jsonl` on the pump's next run. This file is the inventory of
everything else, read off `do_GET`/`do_POST` rather than remembered, so a follow-up can close each
gap or decide to keep the server.

Nothing here is deleted yet. `dashboard.py` still runs.

## Already covered by the board — no gap

These endpoints read data the pump already mirrors into the artifact db every 5 minutes. The
board renders all of it; the only difference is staleness (see "Structural limits" below).

| Endpoint | Board equivalent |
|---|---|
| `GET /api/escalations` | `escalations` collection (`board_state.escalation_docs`) |
| `GET /api/assignments` | `assignments` collection (`assignment_docs`) |
| `GET /api/ado-tickets` | `tickets` collection (`ticket_docs`) |
| `GET /api/tasks` | `sessions` collection (`session_docs`) — **partially**, see below |
| `POST /api/escalations/<id>/answer` | the board's own answer buttons — **partially**, see below |
| `GET /` (serves `dashboard.html`) | the published artifact is the page |

## Gaps: things 4400 does that the board cannot

### 1. Answer an escalation the board refuses to offer a control for

The board's answer buttons appear only when the ledger's newest record for that id is
`needs_human` **and** carries no answer yet **and** the worker offered at least one option — the
same gate `board_mirror_answers.accepted_answers()` applies on the way down, so a wider control
would silently do nothing. That leaves two shapes only 4400 can answer:

- **A record with no options.** The worker asked an open question and offered no choices; the
  board has no free-text field, and the return path deliberately only ever writes a string the
  ledger itself already lists among that record's options.
- **A free-text answer to a record that does have options.** `POST /api/escalations/<id>/answer`
  takes any non-empty string.

To close: a text input on the card, plus a return-path rule for strings the ledger has never
seen — which is a real trust-boundary decision, not a UI change. Today the only value that can
reach the ledger from shared storage is one already in it.

### 2. `POST /api/escalations/<id>/dismiss`

Retires an undeliverable record (`escalations.is_undeliverable`: `needs_human`, an answer already
decided, delivery attempts exhausted). The board shows these — read-only, pointing at 4400 — and
has no control to close one. To close: a second button, plus a `dismiss` arm in the return path.

### 3. The manager chat — four endpoints

- `GET /api/manager/chat` — conversation history plus the busy flag
- `POST /api/manager/chat` — send the manager a message; **spawns a paid manager turn** in a
  local thread (`start_manager_turn`)
- `GET|POST /api/manager/prefs` — read/set the manager's model and effort
- `POST /api/manager/reset` — reset the manager session

None of this is mirrored to the board at all — the board's only manager field is
`meta/status.manager_session_id`. Posting a chat message is not a data write: it starts a local
process. A sandboxed page cannot do that, and the pump is deliberately forbidden from doing
anything but `write_db`/`read_db`. Closing this needs a queue the page writes and the pump drains
into a local action — the same shape as the answer return path, but the action costs money and is
not idempotent, so "appended twice" is a real bill rather than a duplicate row.

### 4. `POST /api/assignments`

Creates an assignment in the ledger **and** notifies the manager (another `start_manager_turn`).
Same structural problem as the chat: the ledger half is a data write the return path could carry,
the notify half is a local process spawn. The daemon's tick does rediscover open assignments, so
the notify is best-effort already — worth knowing if this one is attempted.

### 5. Session fields the board does not publish

`GET /api/tasks` returns the live dev-stack state per worktree that `session_docs` omits
entirely: `ports`, `dev_status`, `mode`, and `path` for registered copies whose session has
already exited. It is also session-first (a session shows up during provisioning, before the
registry has a row), where the board joins the other way. Anyone using 4400 to find which port a
worktree's dev stack is on has no board equivalent.

## Structural limits — not endpoints, but reasons the server survives

- **Subprocesses.** `get_tasks` shells out to `parallel-task.sh`, `git`, `gh`; `get_ado_backlog`
  to `az`. The artifact page is sandboxed and cannot run any of it. Everything the board shows
  from those sources is whatever the pump last fetched — which is why the board's "Làm mới" says
  out loud that it only re-reads the table and does not call ADO.
- **Freshness.** 4400 is live on every request (behind a short TTL cache); the board is at most
  one pump cycle stale, currently 5 minutes. Any workflow that needs sub-minute truth stays on
  4400.
- **Write latency.** An answer on 4400 is in the ledger before the HTTP response returns. An
  answer on the board is in the ledger within one pump cycle. For a worker blocked on a decision
  that is up to 5 more minutes of idle.
- **Availability.** 4400 works with no network and no artifact; the board needs claude.ai and a
  granted db capability. They fail independently, which is a point in favour of keeping one of
  them around while the other is the primary.

## Suggested order for a follow-up

1. **Dismiss** (gap 2) — smallest, same shape as the answer path already built.
2. **Free-text answers** (gap 1) — needs the trust-boundary call made explicitly.
3. **Session ports/dev_status** (gap 5) — pure `board_state.py` additions, no new mechanism.
4. **Manager chat / assignments** (gaps 3, 4) — needs a page→pump command queue with
   exactly-once semantics, because these spawn paid work. Largest, and the only one that would
   make retiring `dashboard.py` a net simplification rather than a net rewrite.

Until at least 1–3 land, keeping `dashboard.py` is the honest answer; it is the only way to
dismiss an undeliverable escalation or answer one the worker left open-ended.
